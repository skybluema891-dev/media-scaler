# Media Scaler Windows 2 受け入れ

検証日 2026年11月22日。Windows 11 Pro x64、Intel Core i7-1165G7、Intel Iris Xe Graphics、メモリ31.6 GiB。検証対象は基準コミット `e1269afc23d5a58c9263f5691562e62093d84aac` のローカル完成版1.2.5。検証開始時のGitHub `main` とローカルHEADが一致し、作業ツリーはクリーンだった。

## 上書き更新の隔離方法

Windows Sandboxを使えないため、Media Scalerのインストーラー登録、対象ショートカット、通常版の設定ディレクトリが存在しないことを確認してから、Windows 2の現アカウントに専用の一時インストール先を作った。OSの標準のスタートメニューとデスクトップにテスト用ショートカットを作成し、通常版の設定ディレクトリには合成設定だけを配置した。開発環境と完成アプリは既存の3フォルダ構成を使用した。

公開版v1.2.4とv1.2.5はGitHub ReleaseのWindowsアセットを取得し、公開SHA-256と照合した。ローカルインストーラーは前回の受け入れ記録のSHA-256と照合した。インストールIDは `{D95D1FD9-8B40-46CE-AF11-32C6599A8C42}`。通常の既定先は `%LOCALAPPDATA%\Programs\MediaScaler`。最初の導入だけ一時ディレクトリを指定し、上書き時はインストーラーの既存インストール先検出とデスクトップタスクの継承を使用した。

| セットアップ | SHA-256 |
| --- | --- |
| 公開v1.2.4 | `fe49aae0fcf74c3900c44898a4e33f4bd3be96a91923b24621b32fe2fe53c18d` |
| 公開v1.2.5 | `a92b2c3584ef93287733802fdb689b4bd263aeb20476eee230b9d290f7f2b45a` |
| Windows 2のローカル1.2.5 | `739be19e234a0ff7b538ed0b8be8c59fc09ac9928f0081e741cd60e63b06de8e` |

各上書きの前に設定JSONとインストール先・アプリ名・実行ファイル・ショートカットの記録を保存した。旧版に戻す場合はアプリを閉じ、テスト用登録とインストール先を確認してからアンインストールし、保存した旧版セットアップを同じテストディレクトリに導入して設定バックアップを戻す。設定の退避とアンインストールを先に行うことで、同じインストールIDの旧版と新版を混在させずに済む。

## 公開v1.2.4からローカル1.2.5

- アプリ名は「メディア・スケーラー」から「Media Scaler」に変わった。インストールIDと配置先を継承し、`media_scaler.exe` と旧ショートカットを削除した。「Media Scaler」のスタートメニューとデスクトップの両ショートカットから同じ新版EXEが起動した。
- 通常版の設定JSONはセットアップの前後でSHA-256が一致した。3倍、指定フォルダ、ファイル名にサイズを付けない設定が起動直後と再起動後の両方で表示された。
- 画像2件と動画1件を一度に追加し、画像1件を一覧から除外した。残るPNGと音声付きH.264 MP4は96×64から288×192へ変換され、FFprobeで確認してFFmpegで全体をデコードした。H.264は `h264_qsv` で書き出し、音声はAACだった。
- 保存先の既存画像はSHA-256が一致し、新しい画像は `image_1.png` として保存された。
- アンインストールでアプリ本体・登録・ショートカットがなくなり、合成設定と既存画像のSHA-256は維持された。

## 公開v1.2.5からローカル1.2.5

- 公開版が手動更新確認で「バージョン 1.2.5 は最新です」と表示した。同じ版番号のローカルビルドをバージョン比較で検出できないため、セットアップを手動で実行した。
- 登録上の版番号は1.2.5のまま、アプリ名とショートカットが更新された。旧実行ファイルのSHA-256は `aa3da26f1998faacb0694aafc8638afb76c193e50fd54fe53f68928fd257e8ab`、新しい実行ファイルは完成アプリと同じ `62208f3f0670106c4cd963126fac3b47763e27d1d446fe316df07264c7394fb2`。設定のSHA-256は前後で一致し、4倍、指定フォルダ、サイズを付ける設定を起動後に確認した。
- この同一版更新のあとも、アンインストールでアプリと登録・ショートカットを撤去できた。合成設定と出力のハッシュは維持された。

## 検出した問題と修正

- Intel Iris Xeで `hevc_qsv` を選択した48×32の変換が0%で停止した。FFmpeg単体でも `faster` や `veryfast` を指定すると停止し、`-global_quality 23` と既定プリセットでは同じ素材を処理できた。HEVC Quick Syncではドライバーの既定プリセットを使用し、品質指定とH.264の既存プリセットを維持する。
- 同梱のWindows版 `libx265` は小さい出力で処理終了時に `0xc0000374` を断続的に返した。プールのみ無効にした試験でも発生した。並列化とSIMDを抑えた試験は16回すべて終了コード0だった。Windowsでこの終了コードが出た場合に限り、途中出力を整理して同じ形式と品質で1回再試行する。
- 深い一時インストール先では、AIプロセスがNumPyの実在ファイルを通常の物理パスから読み込めなかった。同じファイルを短いドライブ名から直接読み込むと成功した。元の深いパスではプレビュー失敗後にFlutterのネイティブ例外も記録された。通常のインストール先に近い長さの一時ディレクトリで追加確認を行った。

## AI、操作、通信

- 比較プレビューは左の元画像96×64と右のAI処理後192×128を表示した。比較境界をスライダーで移動し、一時画像2枚の寸法もFFprobeで読み取った。通常のAI画像保存と、利用者が実際にドラッグ＆ドロップした画像のAI保存も192×128だった。
- テストプロセスだけに接続先のないループバックプロキシを指定し、手動更新確認で接続エラーと変換を続けられる案内を確認した。同じプロセスのVulkanドライバー検出を失敗させ、GPU優先を有効にしたまま画像と動画を処理した。Vulkan初期化失敗がログに残り、CPU処理でPNGと音声付きH.265 MP4を192×128へ出力できた。
- 最初のH.265停止時にGUIのキャンセルを押すと操作可能な状態に戻り、不完全なMP4が残らなかった。処理中の進捗、経過、残り時間の表示を確認した。
- AI変換の出力完成後、短いパスでもGUIのネイティブ異常終了を再現した。同じDLLのPDBでRVA `0x3fea5` を引くと `flutter::FlutterPlatformNodeDelegate::ChildAtIndex + 0x3f` だった。FlutterのWindowsアクセシビリティ処理に同じシンボル・変位の報告がある。配布用Flutterの修正版を確認してから再検証する必要がある。[Flutter issue #195399](https://github.com/flutter/flutter/issues/195399)

- 修正コミットのGitHub Actionsではリリース手順テストとDart静的解析・Flutterテストが成功した。上記の上書き更新や変換の確認は、別途Windows 2で実行した。 [GitHub Actions](https://github.com/skybluema891-dev/media-scaler/actions/runs/44964582052)

## 1080p・2K・4Kの動画性能

Windows 2で同梱のFFmpegとAIワーカーを計測した。合成素材は動きのある映像とAAC音声。通常変換は24 fpsで4秒（96フレーム）、AIは2 fpsで1秒（2フレーム）。入力と出力は1080p（1920×1080→1280×720）、2K（2560×1440→1920×1080）、4K（3840×2160→2560×1440）。通常変換は同じバイキュービック縮小で、CPUはCRF 23、Quick Syncはglobal quality 23。AIは「高速」設定を使用した。比較画像の指標はバイキュービック縮小とのSSIMで、AIによる見た目の改善を判定する用途には使っていない。

時間にはプロセスの起動と終了が含まれる。メモリはWindowsでサンプリングしたプロセスツリー全体のワーキングセットのピークで、GPU専用メモリは含まない。GPU使用率は該当プロセスが使った個別のGPUエンジンのピーク。短い処理でサンプルが取れなかった箇所は未計測とした。計測は短い合成素材を各条件1回ずつ使った。

各欄は実時間（秒）とピークメモリ（MiB）。

| 処理 | 1080p | 2K | 4K |
| --- | ---: | ---: | ---: |
| デコード＋縮小のみ | 1.65 / 未計測 | 1.04 / 未計測 | 2.19 / 未計測 |
| H.264 CPU | 2.60 / 未計測 | 3.59 / 494.2 | 5.54 / 931.9 |
| H.264 Quick Sync | 4.21 / 89.6 | 3.96 / 91.3 | 7.88 / 497.3 |
| H.265 CPU | 6.77 / 379.0 | 7.82 / 622.8 | 20.84 / 1,029.9 |
| H.265 Quick Sync | 5.67 / 260.1 | 5.24 / 362.5 | 9.17 / 572.6 |
| AI Vulkan | 40.51 / 239.0 | 69.61 / 291.8 | 145.40 / 508.0 |
| AI CPU | 148.47 / 198.9 | 180秒で打ち切り / 231.8 | 180秒で打ち切り / 355.2 |

- すべての通常変換で映像96フレームと音声を確認し、FFmpegで映像をデコードした。SSIMは0.9932〜0.9976。4K H.265はQuick SyncがCPUの約2.3倍速く、ワーキングセットも小さかった。4K H.264ではCPUが速かった。Quick SyncのメモリはGPU専用メモリを含まないため、CPU側との合計メモリ比較には使えない。
- デコード＋縮小だけの処理は1.0〜2.2秒。4KのH.265で完了までに時間を要した主な差は、エンコードと関連する音声処理・ファイル書き出しが加わった段階にある。
- Vulkanの3Dエンジンのピークは1080p・2K・4Kで35%、35%、42%。Quick SyncのH.265で取得できたピークは3Dが22〜31%、VideoDecodeが6〜12%。短いサンプリングでVideoEncodeのピークは取得できなかった。
- AIの成功出力は指定寸法のH.264、音声付き2フレームで、SSIMは0.9933〜0.9953。Vulkan実行ファイル内の時間はGPUの総時間40.51／69.61／145.40秒に対し29.40／65.26／137.23秒だった。4Kではバッチ前後が約6.4秒、バッチ処理内でVulkan実行以外が約1.8秒だった。Vulkan実行ファイル内の推論と転送は個別に計測していない。CPUの1080pは148.47秒のうち145.34秒がAIバッチ処理にかかった。

計測の生データは開発環境の `logs/windows2-video-benchmark.json` に保存した。

## 受け入れ判定と公開条件

上書き更新、旧設定の継承、ショートカット、通常の画像・動画変換、AIの出力、通信障害時の継続とアンインストール後のデータ保全を実機で確認した。正式受け入れは未完了。AI処理後のWindows UIの異常終了と、深いカスタムインストール先でのAI依存読み込みを解消し、実機で再検証する必要がある。Windows 2の合成データで検証した範囲に限り、Windows 1の実ユーザーデータは今回の試験に使っていない。

ローカル確認版1.2.6は開発環境の `build/candidate/` に保持した。完成アプリ内の1.2.5を引き続き保管する。公開v1.2.5は同一版番号の新しいビルドを検出しないため、次の正式公開には別のバージョン番号を割り当てる。公開前にmacOSの署名・公証と全OSのビルドおよび実機の条件を確認する。
