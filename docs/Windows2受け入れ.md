## 検出した問題と修正

- Intel Iris Xeで `hevc_qsv` を選択した48×32の変換が0%で停止した。FFmpeg単体でも `faster` や `veryfast` を指定すると停止し、`-global_quality 23` と既定プリセットでは同じ素材を処理できた。HEVC Quick Syncではドライバーの既定プリセットを使用し、品質指定とH.264の既存プリセットを維持する。
- 同梱のWindows版 `libx265` は小さい出力で処理終了時に `0xc0000374` を断続的に返した。プールのみ無効にした試験でも発生した。並列化とSIMDを抑えた試験は16回すべて終了コード0だった。Windowsでこの終了コードが出た場合に限り、途中出力を整理して同じ形式と品質で1回再試行する。
- 深い一時インストール先では、AIプロセスがNumPyの実在ファイルを通常の物理パスから読み込めなかった。同じファイルを短いドライブ名から直接読み込むと成功した。元の深いパスではプレビュー失敗後にFlutterのネイティブ例外も記録された。通常のインストール先に近い長さの一時ディレクトリで追加確認を行った。

## AI、操作、通信

- 比較プレビューは左の元画像96×64と右のAI処理後192×128を表示した。比較境界をスライダーで移動し、一時画像2枚の寸法もFFprobeで読み取った。通常のAI画像保存と、利用者が実際にドラッグ＆ドロップした画像のAI保存も192×128だった。
- テストプロセスだけに接続先のないループバックプロキシを指定し、手動更新確認で接続エラーと変換を続けられる案内を確認した。同じプロセスのVulkanドライバー検出を失敗させ、GPU優先を有効にしたまま画像と動画を処理した。Vulkan初期化失敗がログに残り、CPU処理でPNGと音声付きH.265 MP4を192×128へ出力できた。
- 最初のH.265停止時にGUIのキャンセルを押すと操作可能な状態に戻り、不完全なMP4が残らなかった。処理中の進捗、経過、残り時間の表示を確認した。
- AI変換の出力完成後、短いパスでもGUIのネイティブ異常終了を再現した。同じDLLのPDBでRVA `0x3fea5` を引くと `flutter::FlutterPlatformNodeDelegate::ChildAtIndex + 0x3f` だった。FlutterのWindowsアクセシビリティ処理に同じシンボル・変位の報告がある。配布用Flutterの修正版を確認してから再検証する必要がある。[Flutter issue #195399](https://github.com/flutter/flutter/issues/195399)

## 1080p・2K・4Kの動画性能

Windows 2で同梱のFFmpegとAIワーカーを計測した。合成素材は動きのある映像とAAC音声。通常変換は24 fpsで4秒（96フレーム）、AIは2 fpsで1秒（2フレーム）。入力と出力は1080p（1920×1080→1280×720）、2K（2560×1440→1920×1080）、4K（3840×2160→2560×1440）。通常変換は同じバイキュービック縮小で、CPUはCRF 23、Quick Syncはglobal quality 23。AIは「高速」設定を使用した。比較画像の指標はバイキュービック縮小とのSSIMで、AIによる見た目の改善を判定する用途には使っていない。

時間にはプロセスの起動と終了が含まれる。メモリはWindowsでサンプリングしたプロセスツリー全体のワーキングセットのピークで、GPU専用メモリは含まない。GPU使用率は該当プロセスが使った個別のGPUエンジンのピーク。短い処理でサンプルが取れなかった箇所は未計測とした。計測は短い合成素材を各条件1回ずつ使った。

各欄は実時間（秒）とピークメモリ（MiB）。

| 処理 | 1080p | 2K | 4K |
| --- | ---: | ---: | ---: |
| デコード＋縮小のみ | 1.65 / 未計測 | 1.04 / 未計測 | 2.19 / 未計測 |
| H.264 CPU | 2.60 / 未計測 | 3.59 / 494.2 | 5.54 / 931.9 |
| H.264 Quick Sync | 4.21 / 89.6 | 3.96 / 91.3 | 7.88 / 497.3 |
| H.265 CPU | 6.77 / 379.0 | 7.82 / 622.8 | 20.84 / 1,029.9 |
| H.265 Quick Sync | 5.67 / 260.1 | 5.24 / 362.5 | 9.17 / 572.6 |
| AI Vulkan | 40.51 / 239.0 | 69.61 / 291.8 | 145.40 / 508.0 |
| AI CPU | 148.47 / 198.9 | 180秒で打ち切り / 231.8 | 180秒で打ち切り / 355.2 |

- すべての通常変換で映像96フレームと音声を確認し、FFmpegで映像をデコードした。SSIMは0.9932〜0.9976。4K H.265はQuick SyncがCPUの約2.3倍速く、ワーキングセットも小さかった。4K H.264ではCPUが速かった。Quick SyncのメモリはGPU専用メモリを含まないため、CPU側との合計メモリ比較には使えない。
- デコード＋縮小だけの処理は1.0〜2.2秒。4KのH.265で完了までに時間を要した主な差は、エンコードと関連する音声処理・ファイル書き出しが加わった段階にある。
- Vulkanの3Dエンジンのピークは1080p・2K・4Kで35%、35%、42%。Quick SyncのH.265で取得できたピークは3Dが22〜31%、VideoDecodeが6〜12%。短いサンプリングでVideoEncodeのピークは取得できなかった。
- AIの成功出力は指定寸法のH.264、音声付き2フレームで、SSIMは0.9933〜0.9953。Vulkan実行ファイル内の時間はGPUの総時間40.51／69.61／145.40秒に対し29.40／65.26／137.23秒だった。4Kではバッチ前後が約6.4秒、バッチ処理内でVulkan実行以外が約1.8秒だった。Vulkan実行ファイル内の推論と転送は個別に計測していない。CPUの1080pは148.47秒のうち145.34秒がAIバッチ処理にかかった。

計測の生データは開発環境の `logs/windows2-video-benchmark.json` に保存した。

## 2026年11月22日　Windows AIの継続検証

PR #1 の `23edc2e39a24b3641618513ead637fb3d50a9da1` から継続した。以前の候補1.2.6のEXEのSHA-256は `d81910234d319d7416eecfb722bde39887423015ea4ef20a56f952b727910ff9`。そのコピーを短い配置で起動し、比較画面を開かずに64×48のPNGと音声付き動画をAI変換した。両ワーカーの終了コードは0で、両方の出力をデコードできた。その後、WindowsのアプリケーションイベントにGUIの例外が残った。スライダー操作は再現の必須条件ではなかった。

実行時のFlutterは3.47.3、frameworkは `e8113bf45620cbeb8aff64947ee4c93e16adb4cf`、engineは `06a2e2a110089dff50fe635cffd2a61e1b24fbcd`。旧候補のWERで例外コード `c0000005` と `c000041d`、DLL内の位置 `0x3fea5` を確認した。DLLのSHA-256は `4598eeff31a9b24947083d3722ccfe0ce62aced05c4bd2c717a4b4af492dac9b` で、既存PDB照合記録の `ChildAtIndex + 0x3f` と一致した。端末で確認できた過去の資料はWERレポートとシンボル照合結果で、完全なメモリダンプは見つからなかった。

### 画面側の対策

行の状態と進捗を1つの固定した読み上げ対象で更新する。完了件数は常設のライブ領域で伝え、キャンセル操作とステージ表示を同じ位置に保つ。進捗通知は250ミリ秒ごとと完了時にまとめ、同じステージ名による再描画を省いた。比較スライダーは元画像の割合を読み上げる。画像自体の重複した読み上げを除き、操作可能なスライダーと閉じるボタンを残した。これらはアプリ側の対策で、FlutterのDLLは従来と同じものを使用した。最初の途中候補ではプレビュー失敗から次の操作に移る際にGUIの例外が再発した。上流の修正が公式SDKに入ったことは確認できていない。 [Flutter issue #195399](https://github.com/flutter/flutter/issues/195399)

### 深いパス

Windowsの `LongPathsEnabled=0` のまま、空白と日本語を含む物理ディレクトリに同梱物を配置した。前回の例外は `ModuleNotFoundError: numpy._expired_attrs_2_0`。今回の切り分けでは、実在するNumPyの `_multiarray_umath.cp313-win_amd64.pyd` の絶対パスが279文字、OpenBLAS DLLが298文字になり、通常の組み込みPythonが拡張モジュールを発見できなかった。組み込み環境のモジュール検索パスをWindows拡張長形式にしてからimportすると、同じファイルでNumPy・Pillow・ncnnを読み込めた。ドライブの割り当てやOS設定の変更は不要だった。

286文字の入力ファイルおよび深い場所に生成するプレビューでは、依存のimport後に別のファイルアクセスも失敗した。ワーカーが扱う入力・出力・モデル・比較用原画像にも拡張長パスを適用した。同梱Vulkanツールはパスをスラッシュで連結するため、従来のWindowsパスで渡せる場合に使う。モデルまたは生成用フレーム名が260 UTF-16コード単位以上になる場合は、CPUへの切り替えを画面に表示する。GPU処理が必要な場合は、モデルと作業用出力が収まる浅いローカル配置を選ぶ。ネットワーク共有上での起動は未検証。

Windowsビルドは、再利用する依存キャッシュにある古いワーカーを取り込まないよう、ステージングの際にGitの `ai_worker/worker.py` を配置する。最初にビルド時の入力パスだけを短くしたところ、Inno Setup 6.7.4で包装できたが、190文字のインストール先で `data/flutter_assets/packages/cupertino_icons/assets/CupertinoIcons.ttf` の展開に失敗し、セットアップが変更をロールバックした。

最終インストーラーは拡張長パス対応の公式Inno Setup 7.1.1で作成した。ローカルとCIは `scripts/prepare_inno_windows.ps1` で発行元のSHA-256を照合して同じポータブル版を準備する。既存の6.7.4は復旧用に保持した。インストーラーの入力には物理パスを直接渡し、配布ファイルから管理用の `runtime.json` を除外する。同じ190文字の物理パスへのインストール、登録、起動、アンインストールが終了コード0で完了した。合成設定のハッシュはアンインストール前後で一致した。 [Inno Setup 7の変更履歴](https://jrsoftware.org/files/is7-whatsnew.htm)

### Windows 2での反復結果

配置と画面取得方法の組み合わせごとに3回とし、比較プレビュー、境界操作、画像と音声付き動画の保存、次のファイルの追加、正常終了までを1回とした。合格条件はすべての試行で出力とGUI応答が正常なこと。Windowsのファイル選択ダイアログは両条件でUI Automationを用い、Flutter画面に対する読み取りの有無を切り替えた。OS上の他の支援技術の有無は判定していない。

| 配置 | Flutter画面は画像のみ取得 | Flutter画面をUI Automationでも取得 |
| --- | --- | --- |
| 短い検証配置 | 3/3 完走 | 2/3 完走。3回目はファイル追加操作中に異常終了 |
| 日本語・空白を含む深い検証配置 | 3/3 完走 | 3/3 完走 |

各条件の初回は先行ビルドのランナーで実施し、Dart AOT・エンジン・ワーカーは最終候補と同じハッシュだった。残る8回は最終EXEを使い、7回完走した。この8回のうち深い配置での4回は最終インストーラーから実際に導入したもの。操作ツールの再接続のため起動と終了だけ行った短い配置の1回は集計から除いた。

短い配置の3回目はPID 1860で、ワーカー起動前にWindowsイベント1000が同一PIDに2件記録された。例外は `c0000005` と `c000041d`、どちらもFlutter DLLのRVA `0x8fe43a`。一致するRelease PDB（SHA-256 `484d1da6dfd6b63b59db9757170737180e02da2d62eaa2303b76d275b66e8492`）では `ui::AXNodeData::GetStringAttribute + 0x12` だった。旧候補で確認した `ChildAtIndex + 0x3f` とは別の位置である。同じ根本原因かは未確定。モーダル表示や完了直後に画面と取得ツリーが一致しない例もあり、比較境界の読み上げは実機合格を保留する。クリックによる境界移動と、Tab・Escapeによる比較画面の終了は確認した。
